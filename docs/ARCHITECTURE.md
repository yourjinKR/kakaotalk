# 카톡 — 설계 결정

## 목적과 경계

친구 관리와 일반채팅의 작은 실행 가능한 단위를 만든다. 설치된 카카오톡은 사용자 흐름을 관찰하는 참고 대상이다. 카카오 서버, 인증, 프로토콜, 원본 코드·자산과 연결하지 않는다.

현재 결과물은 **PC 브라우저에서 실행하는 localhost 개발 프로토타입**이다. 합성 사용자 네 명 사이에 HTTP와 SSE로 실제 로컬 송수신이 이루어진다. 사용자 전환은 테스트 도구이며 로그인/인증이 아니다. 인터넷 서비스·다른 PC 접속·Windows 설치 패키지는 아직 없다.

## 기술 선택

| 결정 | 이유와 한계 |
| --- | --- |
| Node.js 22+ 기본 모듈, HTML/CSS/JS | 설치된 Node 22.23.2로 바로 실행하고 외부 패키지 설치 없이 한 기능 사이클을 검증. .NET 런타임은 있으나 SDK는 없어 WPF 개발 환경을 새로 설치하지 않음. |
| HTTP 명령 + SSE 갱신 알림 | 같은 PC의 여러 탭에서 재현 가능한 송수신. 이벤트는 상태 재조회 신호이며 메시지 전달 ACK가 아님. 재접속 시 전체 상태 재조회. |
| JSON 파일, 단일 쓰기 큐 | 최초 최소 구현을 쉽게 실행·점검. 임시 파일 저장→rename 성공 후 메모리 반영. 저장 실패 시 기존 메모리 보존. 트랜잭션 DB·백업·fsync 기반 장애 내구성·다중 프로세스는 후속 과제. |
| 방향성 친구 관계 + hidden, 별도 방향성 blocks | 숨김은 관계와 기존 대화·수신을 유지하고 삭제는 내 방향 친구 관계만 제거. 차단은 내 친구 관계를 제거한 뒤 별도 관계로 저장하며 양쪽의 새 1:1 전송을 막음. 자동 상호 등록은 하지 않음. |
| 사용자 ID 정확검색·친구 이름/ID 부분검색 | 검색 규칙은 자체 정책. 카카오 ID 체계·초성 검색과 동일하다고 주장하지 않음. 합성 ID me/hana/jun/sora만 있음. |
| direct는 두 참여자 조합 재사용, group은 새 방 생성 | 중복 1:1 방을 방지하는 독립 정책. 원본의 재사용/그룹 생성 조건은 미확인. |
| 방별 단조증가 메시지 순번·참여자별 읽음 커서 | 안 읽은 메시지 수와 발신 메시지를 안 읽은 참여자 수를 별도로 계산. 실제 카카오 내부 구조를 추정한 것이 아님. |
| clientId로 송신 재시도 멱등성 | 응답 손실 후 재시도해도 같은 발신자·방·ID이면 한 메시지만 저장. 같은 ID의 다른 본문은 거부. |
| 127.0.0.1 바인딩·출처 검사·정적 파일 허용 목록 | 인증 없는 테스트 프로필을 외부 서비스처럼 노출하지 않기 위한 개발 환경 경계. 실제 계정 인증을 대체하지 않음. |

## 데이터와 불변식

- `users`: id, displayName, statusMessage. 현재는 서버가 생성한 합성 계정만.
- `friendships`: ownerId, userId, hidden. 자기 자신·중복 관계 거부.
- `blocks`: ownerId, userId. 방향성 관계이며 자기 자신·미존재 사용자·중복 차단·같은 방향의 친구 관계와 중복을 거부. 반대 방향의 친구 관계 또는 차단은 독립적으로 유지한다. version 1의 기존 파일에 이 필드가 없으면 메모리에서 빈 배열로 보완하며 열기만으로 파일을 다시 쓰지 않는다.
- `rooms`: direct/group, 참여자, 제목, 생성/갱신 시각, readCursors. direct 2명, group 3명 이상.
- `messages`: roomId, senderId, sequence, text, clientId, createdAt. 방 안에서 순번은 1씩 증가. 본문은 공백만 불가, 최대 4000 UTF-16 코드 단위. 서버는 앞뒤 공백을 제거한다.
- 방의 안 읽은 수: 내 커서보다 뒤이며 내가 보내지 않은 메시지의 수.
- 메시지 옆 안 읽은 수: 발신자를 제외하고 해당 메시지 순번에 도달하지 않은 참여자 수.
- GET과 메시지 송신은 읽음을 변경하지 않는다. 프런트는 선택된 방의 메시지를 렌더한 뒤 문서가 visible이고 focus이며 대화 하단을 보고 있을 때 해당 순번까지 읽음을 요청한다. 송신 중 도착한 상대 메시지를 보지 않고도 읽었다고 처리하는 경쟁 상황을 방지한다. 이 규칙은 자체 설계다.
- 방 조회·전송·읽음 요청은 선택된 데모 사용자가 참여자여야 한다. 쿼리의 데모 사용자 선택은 보안 인증이 아니다.
- 1:1 방의 새 메시지는 양방향 중 어느 쪽에든 차단이 있으면 거부한다. 기존 내역 조회·읽음과 그룹 메시지에는 차단을 적용하지 않는다. 차단 전에 저장된 메시지의 같은 `clientId`·본문 재요청은 기존 결과를 반환하며, 새 전달을 발생시키지 않는다.

## 다음 구조 변화의 기준

1. 실제 인증·계정 관리와 DB가 준비되기 전까지 localhost 제한 유지.
2. 데스크톱 패키징 전에도 도메인/API 검증은 계속 독립 실행 가능하게 유지.
3. 새 기능마다 근거 ID→자체 정책→코드→검증을 연결. 근거가 상충하면 미확인으로 유지.
4. 차단은 친구 표시 상태와 메시지 전달 정책을 분리한다. 그룹 차단·프로필 비공개를 추가할 때 기존 차단과의 관계를 별도로 설계한다.
5. 그룹 초대/탈퇴 추가 시 참여 시점별 메시지 공개·읽음 분모 정책을 먼저 정할 것.

## 친구 삭제 — 2026-10-23, 두 번째 기능 묶음

### 근거와 확인 범위

- [OBS-R08](research/installed-resource-flows.md): 배포 문자열에 삭제 항목·결과·자동 등록 제외 안내가 있고, 일부 안내에 삭제 후 메시지 수신 가능이라는 설명이 있다. 문자열 존재는 실행 동작의 증명이 아니다.
- [OBS-UI05](research/runtime-ui-observations.md): 실제 친구 메뉴에 삭제 항목이 표시되었다. 원본 확인창·완료 결과·재추가 정책은 여전히 미확인이다.
- 이번 기능에서는 기존 관찰을 재사용했다. 명시된 원본 테스트 계정/대상이 없어 원본 관계를 변경하거나 추가 관찰하지 않았다. 아래 내용은 **독립 앱의 자체 정책**이며 새로운 REA Evidence나 원본 UI 관찰이 아니다.

### 자체 정책과 구현

1. 삭제는 `ownerId → userId` 관계만 제거한다. 일반/숨긴 친구에 동일하게 적용하며 상대방의 친구 관계, 계정, 기존 1:1/그룹방, 메시지, 읽음 커서는 유지한다. 방 참여자는 친구 여부와 독립적이므로 삭제만으로는 송수신을 중단하지 않는다. 별도 차단이 있다면 아래 차단 정책을 적용한다.
2. 자동 친구 등록 기능은 없다. 삭제 이력을 위한 tombstone도 두지 않는다. ID로 직접 재추가하면 `hidden:false` 관계를 만들며 기존 1:1 방을 재사용한다. 향후 연락처 자동 등록을 추가할 때 삭제 이력/재등록 정책을 별도로 설계해야 한다.
3. 프로필의 `친구 삭제`, 숨긴 친구 관리의 `삭제`가 같은 확인창을 연다. 이름·ID와 대화/수신 유지·재추가 가능 안내를 보여 준다. 기본 초점은 취소이며 취소/닫기/Escape는 요청하지 않는다. 제출 중에는 중복 제출과 창 닫기를 막고, 실패 시 오류와 재시도 가능한 확인창을 유지한다.
4. 본문 없는 `DELETE /api/friends/:friendId?user=ownerId` → `200 { userId, deleted }`. 이미 관계가 없는 유효 사용자는 `deleted:false`로 성공하여 응답 유실 후 재시도할 수 있다. 자기 자신/빈 ID는 400, 미존재 사용자는 404다. 이는 현재 관계를 제거하는 연산이므로 삭제 후 별도 재추가가 완료된 뒤 다시 보낸 DELETE는 새 관계도 제거한다. 정확한 요청 식별자를 보존하는 멱등성 키는 없다.
5. 기존 쓰기 큐와 임시파일→rename을 재사용한다. 저장 성공 후에만 메모리와 삭제한 사용자의 SSE를 갱신하고, 실패하면 관계와 알림을 보존한다. 이미 관계가 없으면 저장·알림을 하지 않는다. 저장 스키마는 version 1을 유지한다.
6. 서버 재조회 시 목록·열린 프로필·숨김 관리·새 채팅의 선택 상태를 맞춘다. 삭제된 프로필은 닫고 열린 대화는 유지한다. 새 채팅에서 삭제/숨김된 친구는 선택에서도 제거한다. 모달 갱신은 체크박스 초점을 보존하고 생성 요청 중 버튼을 다시 활성화하지 않는다. 비친구 대상 방 생성 API는 허용하되 아래 차단 정책을 적용한다.

구현: `server/store.mjs`, `server/index.mjs`, `public/app.js`, `public/index.html`, `public/styles.css`. 검증: [친구 삭제 검증](validation/session-02.md), `test/friend-deletion.test.mjs`.

## 친구 차단/해제 — 2026-10-23, 세 번째 기능 묶음

### 기존 근거와 미확인 범위

- [OBS-R07](research/installed-resource-flows.md): 배포 문자열에는 차단 시 메시지 수신 중단과 친구목록 제거 안내, 메시지 차단과 프로필 비공개를 구분하는 항목이 있다. 이는 일반 파일 관찰이며 실행 동작이나 REA Evidence가 아니다. 양방향 전송·기존 대화·그룹방의 처리 규칙은 확인되지 않았다.
- [OBS-UI05](research/runtime-ui-observations.md): 원본 친구 관리 메뉴에서 차단 항목의 표시만 관찰했다. 차단 확정·해제·송수신 결과는 관찰하지 않았다.
- 해제 안내는 상충한다. `IDS_CONTACT_100019`(S:1937)는 즉시 재추가할 수 없다는 안내, `IDS_FRIENDMNGRLSTCTRL_100015`(S:7918)는 해제 후 추가 여부 질문, `IDS_ADDFRIENDDLG_100032`(S:7828)는 해제 후 등록 완료 안내다. 현재 원본 정책을 하나로 확정하지 않는다.
- 이번 기능은 기존 기록을 재사용하며 새 원본 조사나 원본 관계 변경을 하지 않는다. 아래 정책·API·저장 구조는 모두 **독립 앱의 자체 설계**다.

### 자체 정책

| 상황 | 독립 앱의 처리 |
| --- | --- |
| 내가 상대를 차단 | 내 방향의 일반/숨긴 친구 관계를 제거하고 `blocks`에 내 방향 차단을 저장한다. 유효한 비친구도 차단할 수 있다. 상대의 친구 관계·차단 상태는 바꾸지 않는다. |
| 친구 목록과 새 채팅 대상 | 내가 차단한 상대를 일반/숨긴 친구 목록과 새 채팅 선택에서 제외한다. 차단 중 ID 친구 추가도 거부하며 먼저 해제해야 한다. 상대가 나를 차단했다는 이유로 내 친구 관계를 제거하지 않는다. |
| 기존 1:1 내역·읽음 | 방·메시지·읽음 커서를 삭제하거나 숨기지 않는다. 두 참여자는 계속 과거 내역을 조회하고 명시적으로 읽음 위치를 갱신할 수 있다. |
| 새 1:1 송신·방 시작 | 어느 방향이든 차단이 있으면 양쪽의 새 메시지 저장과 1:1 방 생성/재사용 요청을 거부한다. 한쪽만 전송되는 상태나 나중에 전달할 보류 메시지는 만들지 않는다. 기존 방은 목록에서 열어 조회할 수 있다. |
| 차단 전 저장된 메시지 재시도 | 동일한 방·발신자·`clientId`·정규화 본문이면 이미 저장한 메시지의 결과를 반환한다. 차단 검사는 새 메시지에만 적용하며 같은 `clientId`의 다른 본문은 기존처럼 409로 거부한다. |
| 그룹 메시지·읽음 | 기존 그룹에서는 차단 관계와 무관하게 모든 참여자의 메시지·수신·읽음과 미확인 참여자 수 계산을 유지한다. |
| 새 그룹 생성 | 생성자가 직접 차단한 사용자를 포함하는 요청은 거부한다. 상대가 생성자를 차단했거나 다른 참여자끼리 차단했다는 이유로 생성하지 못하게 하지는 않는다. 그룹 초대/탈퇴는 아직 범위 밖이다. |
| 내가 차단 해제 | 내 방향 차단만 제거한다. 친구로 자동 복귀하지 않으며 이후 ID로 다시 추가할 수 있다. 반대 방향 차단이 남아 있다면 1:1 전송과 방 시작 제한은 계속된다. |

프로필 비공개, 연락처 자동 등록, 원본 카카오톡과의 동기화는 구현하지 않는다. 일반적인 1:1 사용 불가 안내를 보여 주지만 `canSend`와 요청 실패를 통해 사용 가능 상태는 드러난다. 상대에게 차단 사실을 숨기는 보안·프라이버시 보장을 주장하지 않는다. 특히 현재 데모 사용자 선택은 인증이 아니며 합성 계정만 사용하는 localhost 프로토타입이다.

### API·저장·화면 반영

1. `POST /api/blocks?user=ownerId`의 JSON 본문은 `{ userId }`, 본문 없는 `DELETE /api/blocks/:target?user=ownerId`는 차단 해제다. 두 요청 모두 성공 시 `200 { userId, blocked, changed }`를 반환한다. 이미 차단/해제 상태면 `changed:false`로 성공하며 저장과 알림을 하지 않는다. 유효하지 않은 대상, 자기 자신 또는 미존재 대상은 거부한다. 요청 식별자는 없으므로 해제 뒤 오래된 차단 요청을 다시 보내면 현재 관계를 차단한다.
2. bootstrap은 내 방향 차단 대상의 `blockedUsers`와 1:1 방의 `canSend`를 제공한다. 내 목록 갱신과 상대의 열린 대화 입력 상태 갱신을 위해 차단/해제 저장이 성공한 뒤 소유자와 대상 모두에게 SSE 변경 알림을 보낸다. 차단을 요청하는 주체의 친구 관계 제거와 차단 추가는 한 번의 저장으로 처리한다.
3. 기존 단일 쓰기 큐와 임시 파일→rename을 사용한다. 저장이 실패하면 친구·차단·대화 상태와 알림은 변경하지 않으며 다음 요청을 처리할 수 있다. 새 메시지와 차단이 겹치면 큐에서 먼저 저장된 연산을 기준으로 적용한다.
4. 저장 형식은 version 1에 `blocks` 배열을 추가한다. 이전 파일에 필드가 없으면 메모리에서만 `[]`로 보완하고 이후 실제 변경 저장 시 포함한다. 필드가 존재하면서 배열이 아니거나, 잘못된 대상·자기 차단·중복 차단·같은 방향의 친구 관계와 겹침이 있으면 손상으로 거부하며 파일을 덮어쓰지 않는다.
5. 차단 확인은 일반/숨긴 친구와 대화상대 목록에서 진입하고 차단 목록 또는 대화상대 목록에서 해제한다. 대화상대 목록에서는 비친구도 처리할 수 있다. 확인창에 1:1 제한·기존 내역/그룹 유지·해제 후 별도 재추가를 안내한다. 취소/Escape는 요청하지 않으며 제출 중 중복/닫기를 막는다. 실패하면 대상과 오류를 유지하여 재시도할 수 있다.
6. 다른 창의 차단/해제도 재조회로 반영한다. 제거된 친구의 프로필과 새 채팅 선택을 정리하고 열린 1:1 내역과 작성 중 본문을 유지한다. 1:1 전송 불가 상태에서 입력은 읽기 전용, 새 전송은 비활성화한다. 해제 후에는 반대 차단 여부를 재조회하기 전까지 기존 전송 제한을 유지한다. 차단/해제·삭제 ACK 뒤 관계 revision을 증가시켜 그 전에 시작된 bootstrap 응답이 확정 상태를 덮지 못하게 한다. 서버는 화면 상태와 무관하게 같은 정책을 검증한다.

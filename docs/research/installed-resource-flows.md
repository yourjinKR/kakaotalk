# 설치 리소스에서 확인한 친구·채팅 흐름

조사일: 2026-10-23 (Asia/Seoul). 범위: 설치 패키지의 공개 배포 리소스만 읽기. 앱을 실행하거나 조작하지 않았고, 사용자 데이터베이스·메시지·계정·인증정보를 읽지 않았다. 원본 코드·이미지·아이콘·리소스 파일을 프로젝트에 복사하지 않았다.

이 문서의 `OBS-R*`는 **일반 파일 도구로 얻은 로컬 정적 관찰 번호**다. REA가 발급한 Evidence ID가 아니다. 별도의 REA 조사 결과와 함께 읽는다. 문자열 존재는 배포 문구의 존재를 확인하며, 현재 실행 경로·서버 정책·활성 UI를 입증하지 않는다.

## 대상과 자료 신원

- 설치 루트: `C:\Program Files (x86)\Kakao\KakaoTalk` (이하 `INSTALL`).
- `KakaoTalk.exe`의 Windows 버전 메타데이터: FileVersion, ProductVersion 모두 `26.9.0.5337`.
- `S` = `INSTALL\skin\default\resource\string_merge.xml`, 1,353,901 bytes, SHA-256 `B724986FC17B644287564BB263E7DD97AEA267D5EA0443A6F9D99276A387B5EC`.
- `C` = `INSTALL\ChangeLogs_ko.md`, 8,714 bytes, SHA-256 `7504A2ECC02611129FE2A6F8C6027BB1FC1532292C3783B30AF5F5FA970FD08F`.
- `S`는 UTF-8 BOM 및 XML 선언을 갖고, PowerShell XML 파서로 `Items/String`을 파싱했다. 항목은 `ID` 속성과 `ko/en/ja` 자식 노드로 구분된다. 아래 line은 설치 파일의 1-based 한국어 `ko` 행이다. ID를 함께 남겼으므로 업데이트 시 해당 항목을 다시 찾을 수 있다.
- `layout/*.xml` 표본은 파일 확장자와 달리 평문 XML이 아니었다. 디코딩·복호화하지 않았고, 아래 파일명은 보조 단서일 뿐 컨트롤/동작 구조로 간주하지 않는다.

## 상충하는 근거를 유지할 것

`IDS_CONTACT_100019`(S:1937)는 차단 해제 시 즉시 친구로 추가할 수 없다고 설명한다. 그러나 `IDS_FRIENDMNGRLSTCTRL_100015`(S:7918)는 해제 후 바로 추가 여부를 묻고, `IDS_ADDFRIENDDLG_100032`(S:7828)는 해제 후 등록 완료를 설명한다. 옛 리소스 잔존, 다른 진입 경로, 조건별 분기의 가능성이 있으나 확인되지 않았다. **현재 카카오톡의 차단 해제 정책을 하나로 단정하지 않는다.** MVP에서 해제 후 관계 상태를 선택한다면 독립 설계 결정으로 표시해야 한다.

## 배포 자료에 기반한 흐름 가설

1. 친구 탭 → 이름 검색 → 친구 선택/프로필 → 1:1 대화. [OBS-R01, R05, R10]
2. 친구 추가 → 연락처 또는 ID 선택 → 입력/검색 → 상태별 결과 → 등록 → 1:1 대화 시작. [OBS-R02~R05]
3. 친구 관리 → 숨김/복귀, 차단/해제, 삭제를 서로 구분. [OBS-R06~R08; 해제 정책은 상충]
4. 채팅 탭 → 방/참여자 검색 또는 기존 방 열기 → 대화 읽기/쓰기 → 송신 성공·실패·재시도. [OBS-R09, R12, R13]
5. 새 채팅 → 대화상대 선택/검색 → 확인 → 그룹 생성; 기존 그룹에서는 참여자 초대. [OBS-R10, R11]

위 순서는 문자열 묶음에서 복원한 가설이다. 클릭 가능한 UI 순서를 실제로 재현한 결과가 아니다.

1. 기존 REA 증거와 파일 해시를 비교하여 같은 설치 버전인지 확인한다. 동일하면 이 정적 조사를 반복하지 않는다.
2. 사용 가능한 Windows UI 관찰 수단으로 친구 탭/채팅 탭, 이름 검색, 추가 창, 대화상대 선택 창의 실제 진입 순서와 취소 경로를 확인한다. 실제 타인에게 메시지·초대를 보내거나 관계를 바꾸는 동작은 테스트 계정/명시적 대상 없이 수행하지 않는다.
3. 친구 숨김·차단·삭제의 확인창과 차단 해제 후 재추가 상충을 우선 해결한다.
4. 메시지별 안 읽은 숫자·읽음 트리거·1:1 방 재사용은 두 테스트 참여자가 있어야 확인할 수 있다. 없으면 미확인 상태를 유지한다.
5. 독립 구현은 위에서 관찰한 사용자 기능만 참고하고, 네트워크 프로토콜·인증·저장 암호화는 자체 서비스에 맞게 설계한다.
